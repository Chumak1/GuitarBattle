# Guitar Skills: как считается рейтинг

Документ описывает фактическую реализацию в
`GuitarBattleServer/app/services/guitar_skills.py` (миграция
`0035_guitar_skills`). Все значения компонентов — от 0 до 100.

```
Guitar Skills = 0.35 × A + 0.20 × C + 0.10 × S + 0.25 × D + 0.10 × P
```

- **A** — Accuracy (точность последних зачётных исполнений), 35%.
- **C** — Challenge (сложность и длина песен), 20%.
- **S** — Score Performance (эффективность игровых очков), 10%.
- **D** — Duel Performance (результаты online-дуэлей), 25%.
- **P** — Player Progression (Level и XP), 10%.

Итог округляется до одного знака после запятой. Компоненты также
хранятся/возвращаются с одним знаком.

---

## 1. Какие события вообще попадают в расчёт

### Solo (Online)

Берутся только зачётные завершённые попытки:

- `game_sessions.mode IN ('normal', 'daily')`;
- `status = 'finished'`;
- есть строка `scores`;
- `completion_percent >= 80`.

`practice` и `preview` исключены. Study вообще не создаёт серверную
сессию, поэтому в рейтинг не попадает.

Точность события для solo — `scores.accuracy_percent`, то есть та
точность, которую клиент подсчитал по существующей формуле попаданий.
Сервер её только ограничивает диапазоном 0..100.

Количество нот — `scores.notes_total`, если оно известно. Иначе note-фактор
считается нейтральным (1.0), а уверенность события снижается. Выдуманных
значений нет.

Сложность — `songs.difficulty` (1..10), заданная администратором.

### Online-дуэли

Берутся только:

- `duel_matches.mode = 'online'`;
- `status = 'finished'`;
- два реальных (не бот) участника;
- у обоих заполнены `result` и `rating_before`.

Бот-дуэли и незавершённые матчи исключены.

Точность дуэли переиспользует существующую формулу
`duel_rules.accuracy_factor`:

```
accuracy = (perfect + great × 0.85 + good × 0.70) / notes_played
```

и переводится в проценты. Это та же формула, по которой сервер считает
точность дуэли в остальных местах; второй формулы не создаётся.

Количество нот — `duel_matches.note_count`; если его нет, используется
`notes_played`; иначе note-фактор нейтральный.

Сложность — сложность песни матча.

Все события идемпотентны по `event_key`:

- `solo:<session_id>`;
- `duel:<match_id>:<user_id>`.

Повторная обработка того же матча/сессии ничего не меняет.

---

## 2. Окно истории

Для A, C и S берётся **последние 30 зачётных событий** пользователя
(solo + online-дуэли вместе), отсортированных по `occurred_at DESC, id DESC`.

Для D берётся **отдельное окно последних 30 online-дуэлей**.

`events_counted` в ответе API — это общее количество зачётных событий
пользователя за всё время, а не размер окна. Уверенность при этом считается
по размеру окна.

---

## 3. Веса одного события

Для каждого события `i` (0 — самое новое):

```
Recency(i)    = 2 ^ (-i / 10)
Difficulty    = 0.60 для сложности 1..3 (Easy)
                0.80 для сложности 4..7 (Normal)
                1.00 для сложности 8..10 (Hard)
NoteFactor    = clamp(sqrt(note_count / median_note_count), 0.75, 1.25)
```

`median_note_count` — медиана количества нот по опубликованным
соревновательным песням. На production сейчас **86**. Если длина чарта
неизвестна, `NoteFactor = 1.0`.

Базовый вес события:

```
W(i) = Recency(i) × Difficulty(i) × NoteFactor(i)
```

### Ограничение повторов одной песни

Перед расчётом A и C весам применяется per-song cap:

```
average_weight = Σ W(i) / N
cap            = 2 × average_weight
```

Если суммарный вес одной песни больше `cap`, **все** события этой песни
масштабируются на `cap / сумма_песни`. Никакого перераспределения веса
другим песням нет — иначе одна песня могла бы вытеснить всё остальное.
Это и есть защита от фарма одной лёгкой композиции.

---

## 4. A — Accuracy (35%)

```
A = 100 × Σ(accuracy_i × W_capped(i)) / Σ W_capped(i)
```

где `accuracy_i` — точность события от 0 до 1 (то есть 100% = 1.0).

Смысл: точность последних исполнений, но:

- свежие результаты весят больше;
- сложные песни весят больше;
- длинные песни весят больше;
- бесконечно повторять одну песню нельзя (cap).

Если зачётных событий нет, `A = 50` (нейтральное значение), уверенность 0.
Ноль не подставляется.

### Что показывает колонка ACC в глобальном рейтинге

Это **не** компонент A. В ответе `/leaderboard/global` есть два разных поля:

- `accuracy_score` — компонент A (взвешенный, 0..100);
- `accuracy_percent` — **простое арифметическое среднее** сырых точностей
  тех же последних 30 событий:

```
accuracy_percent = 100 × Σ(raw_accuracy_i) / N
```

Оно не учитывает recency, сложность, длину и per-song cap. Именно
`accuracy_percent` клиент показывает в колонке **ACC**.

Пример: 10 событий по 100% на Easy и 20 событий по 80% на Hard.

- ACC = `(10×100 + 20×80) / 30 = 86.67%`.
- A будет другим: Hard-события получают больший вес (1.0 против 0.6),
  поэтому вклад 80% на Hard сильнее, чем вклад 100% на Easy. Точное
  значение A зависит ещё и от давности событий.

Старые клиенты, которые ещё не знают `accuracy_percent`, показывают
legacy-поле `best_accuracy` (лучшая точность по старым рекордам). Новый
клиент использует `accuracy_percent`, а при его отсутствии — `best_accuracy`.

---

## 5. C — Challenge (20%)

Для каждого события:

```
ChallengePerformance_i = accuracy_i × Difficulty_i × NoteFactor_i / 1.25
C = 100 × Σ(ChallengePerformance_i × W_capped(i)) / Σ W_capped(i)
```

Важно: `Difficulty` и `NoteFactor` входят и в само значение
`ChallengePerformance`, и в вес `W` (то же самое требование «использовать
те же веса» из спецификации). Поэтому вклад сложной и длинной песни
усиливается дважды. Это сделано намеренно и зафиксировано тестами:
идеальное исполнение Easy даёт C ≈ 48, идеальное исполнение Hard — C = 80.

Смысл: сложная песня сама по себе не даёт высокий C. Нужна ещё и высокая
точность. Hard с большим количеством ошибок не должен автоматически
обыгрывать чистое исполнение Easy/Normal.

Если истории нет, `C = 50`, уверенность 0.

---

## 6. S — Score Performance (10%)

Для каждого события, где известна длина чарта:

```
ScoreEfficiency_i = clamp(score_i / (note_count_i × 100), 0, 1)
S = 100 × Σ(ScoreEfficiency_i × Recency_capped(i)) / Σ Recency_capped(i)
```

- Вес — только recency (сложность и длина уже сидят в значении через
  `note_count`).
- Применяется тот же per-song cap, что и для A/C.
- События без `note_count` из S исключаются; если не осталось ни одного,
  `S = 50`, уверенность 0.

`score_i` — реальные игровые очки:

- solo — `scores.score_points` (клиентский счёт с множителями сложности,
  BPM, уровня песни и комбо-бонусом);
- дуэль — `duel_participants.score_points` (очки дуэльных категорий
  Perfect/Great/Good).

«Максимум» для S — `note_count × 100`. Это базовая шкала, а не
теоретический максимум клиентского solo-счёта со всеми множителями и
комбо. Поэтому S — относительная эффективность очков, а не абсолютное
сравнение solo и дуэлей. Ограничение известно и не влияет на сортировку
сильнее, чем A/C/D.

---

## 7. D — Duel Performance (25%)

Только online-дуэли между людьми, последние 30 матчей.

Для каждого матча:

```
Outcome = 1.0 победа, 0.5 ничья, 0.0 поражение
Margin  = my_score / (my_score + opponent_score)
          (0.5, если оба счёта нулевые)
ActualPerformance = 0.70 × Outcome + 0.30 × Margin
```

Предматчевая сила игрока:

```
Strength = 0.70 × NormalizedGuitarSkills
         + 0.30 × NormalizedLevel

NormalizedLevel        = 100 × clamp(level / 50, 0, 1)
NormalizedGuitarSkills = Guitar Skills на момент до матча (0..100)
```

Для новых дуэлей `duel_participants.guitar_skills_before` фиксирует
предматчевый Guitar Skills обоих игроков. Для исторических матчей, где
этого поля нет:

```
NormalizedGuitarSkills ≈ 100 × clamp(rating_before / 2000, 0, 1)
```

и уверенность D снижается — значение не выдумывается.

Ожидаемый результат (Elo-подобная формула):

```
ExpectedScore = 1 / (1 + 10 ^ ((OpponentStrength - PlayerStrength) / 25))
```

`Scale = 25` — настраиваемый параметр.

```
DuelDelta_i = ActualPerformance_i - ExpectedScore_i
```

`DuelDelta` усредняется по матчам с весами recency (без per-song cap,
матчи — не песни). Чтобы 1–2 дуэли не давали резких скачков:

```
Reliability = match_count / (match_count + 10)
D = clamp(50 + 80 × WeightedAverage(DuelDelta) × Reliability, 0, 100)
```

Если дуэлей нет: `D = 50`, уверенность 0.

---

## 8. P — Player Progression (10%)

```
LevelScore = 100 × clamp(level / 50, 0, 1)
XPScore    = 100 × clamp(xp_total / 344756, 0, 1)
P          = 0.70 × LevelScore + 0.30 × XPScore
```

- `50` — `level_normalization_max` по умолчанию.
- `344756` — XP, необходимый для уровня 50 по текущей кривой (`xp_reference`).
  Это **фиксированный** ориентир, а не максимум XP среди пользователей.
- P считается всегда, даже без зачётных событий: новый аккаунт 1 уровня
  имеет P ≈ 1.4, а не 50.

---

## 9. Итог, уверенность и provisional

```
Guitar Skills = 0.35×A + 0.20×C + 0.10×S + 0.25×D + 0.10×P
```

Все компоненты перед подстановкой уже округлены до 0.1, итог — тоже.

### Уверенность (confidence)

- A/C/S: `min(1, events / 10)`, где `events` — число событий в окне;
- D: доля матчей с известными pre-match skills × `min(1, duels / 10)`;
- P: 1.0.

Общая уверенность — взвешенная сумма уверенностей компонентов теми же
весами 0.35/0.20/0.10/0.25/0.10.

### Provisional

```
provisional = confidence < 0.35
              OR total_ranked_events < 5
```

Provisional-игроки показываются в таблице, но помечены `PROV` (в клиенте).
Нейтральные 50 за отсутствие истории — это не «нулевой рейтинг», а
честное «недостаточно данных».

## 10. Глобальный leaderboard

Публичная таблица `/api/v1/leaderboard/global`:

- включает только активных пользователей, у которых есть хотя бы одно
  зачётное событие;
- аккаунты без событий (новые, только Practice/Preview, админы) получают
  нейтральный снимок для админ-панели, но не занимают место в таблице;
- сортировка:

```
guitar_skills DESC,
duel_performance DESC,
xp_total DESC,
username ASC
```

- `position_change = previous_rank - rank` (положительное — игрок поднялся),
  `null` при первом расчёте;
- legacy-поля `rating_points`, `games_played`, `best_accuracy` сохранены
  для старых клиентов, но больше не являются ключом сортировки.

В карточке игрока `/leaderboard/global/{user_id}` дополнительно отдаются:

```
components.accuracy   = { value, events, confidence }
components.challenge  = { value, events, confidence }
components.score      = { value, events, confidence }
components.duel       = { value, events, confidence }
components.progression= { value, events, confidence }
```

и `calculation_version`, `last_calculated_at`.

---

## 11. Когда пересчитывается

- После каждой зачётной solo-песни — в той же транзакции, только этот игрок.
- После каждой online-дуэли — фиксируются pre-match skills, пишутся два
  события, пересчитываются оба игрока.
- При изменении конфигурации — bump `calculation_version`, запись в
  историю, фоновый полный пересчёт с process-lock.
- Вручную из админки — `POST /admin/guitar-skills/recalculate`
  (`dry_run` сначала рекомендуется).
- Backfill и повторный пересчёт идемпотентны: `event_key` не даёт
  задвоить событие, история пишется только при реальном изменении значения.

## 12. Конфигурация по умолчанию (production)

| Параметр | Значение |
|---|---|
| Веса | A 0.35, C 0.20, S 0.10, D 0.25, P 0.10 |
| Окно | 30 событий |
| Recency decay | 10 |
| Easy / Normal / Hard | difficulty 1–3 / 4–7 / 8–10 |
| Множители сложности | 0.60 / 0.80 / 1.00 |
| Note factor | clamp 0.75..1.25 |
| Median note count | 86 (на production) |
| Level normalization max | 50 |
| XP reference | 344 756 (уровень 50) |
| Duel strength | Guitar Skills 0.70, Level 0.30 |
| Expected score scale | 25 |
| Reliability constant | 10 |
| Per-song cap | 2 average attempts |
| Confidence expectations | 10 событий / 10 дуэлей |
| Provisional threshold | 0.35 |
| Min ranked events | 5 |

Все параметры меняются в админ-панели **Guitar Skills**; при сохранении
проверяется, что пять весов дают ровно 100% (±0.0001), после чего
запускается контролируемый пересчёт.

## 13. Короткие примеры

1. **Новый игрок, 1 уровень, без истории.**
   A=C=S=D=50, P≈1.4 → итог ≈45.1, `provisional=true`. Это не ноль:
   просто данных мало.

2. **Идеальное исполнение одной Easy-песни.**
   A=100, C≈48, S зависит от очков, D=50 (дуэлей нет), P зависит от
   уровня. Высокий A не делает итог максимальным: D и P тянут вниз.

3. **Идеальное исполнение Hard.**
   A=100, C=80 (при note-факторе 1.0), S обычно высокий. Итог заметно
   выше, чем у Easy при той же точности.

4. **Игрок с высоким Level/XP, но слабой текущей игрой.**
   P даёт свой вклад, но A/C/D падают; высокий Level не удерживает его
   на вершине.

5. **Одна лёгкая песня, сыгранная 20 раз.**
   Per-song cap ограничивает суммарный вес этой песни двумя средними
   попытками; остальные песни и дуэли получают нормальный вес.

6. **Поражение сильному сопернику с минимальной разницей.**
   `ActualPerformance` близок к `ExpectedScore`, `DuelDelta` маленький →
   D почти не падает. Крупное поражение новичку даёт большой отрицательный
   delta и заметно снижает D.

---

## 14. Что важно не путать

- **ACC в таблице** (`accuracy_percent`) — простое среднее сырых точностей
  последних 30 событий, без весов.
- **A / accuracy_score** — взвешенная точность с учётом свежести, сложности,
  длины и cap. Это 35% итогового Guitar Skills.
- **XP и Level** — отдельные показатели. Они входят только в P (10%) и не
  подменяют мастерство.
- **Practice и Study** не влияют ни на A/C/S/D, ни на XP, ни на Level.
- **Score S** — относительная эффективность очков, а не абсолютное
  сравнение solo и дуэлей; для solo максимум `note_count × 100` является
  базовой шкалой, а не теоретическим максимумом клиентского счёта.
