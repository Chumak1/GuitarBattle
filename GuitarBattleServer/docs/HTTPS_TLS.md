# HTTPS, certificates and security headers (fretfight.online)

Production edge for `https://fretfight.online`. The API container itself is a
plain HTTP service on `127.0.0.1:8000`; everything TLS-related happens in Caddy
on the VM.

## Topology

| Piece | Where | Notes |
|---|---|---|
| DNS | Yandex Cloud DNS zone `fretfight-online` | `fretfight.online` and `www.fretfight.online` point at the VM |
| Caddy 2.6 | host, `systemd` unit `caddy`, config `/etc/caddy/Caddyfile` | listens on `*:80`, `*:443` TCP and `*:443` UDP (HTTP/3) |
| FastAPI | Docker Compose service `api` | published only as `127.0.0.1:8000` (`API_BIND_HOST`) |
| Certificates + ACME account | host disk `/var/lib/caddy/.local/share/caddy` | specified explicitly with the `storage file_system` global option |

The Caddy config is versioned in this repository as [`deploy/Caddyfile`](../deploy/Caddyfile).
Edit that file, not the copy on the server, then apply it:

```bash
cd /opt/guitarbattle/GuitarBattleServer
sudo install -o root -g root -m 0644 deploy/Caddyfile /etc/caddy/Caddyfile
sudo caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
sudo systemctl reload caddy          # graceful reload, no downtime
```

`pwsh -File scripts/deploy-prod.ps1 -Caddy` does the same three steps as part of
a normal deploy. Every change made by hand leaves a
`/etc/caddy/Caddyfile.bak-<timestamp>` next to the live file; roll back with

```bash
sudo cp -a /etc/caddy/Caddyfile.bak-<timestamp> /etc/caddy/Caddyfile
sudo systemctl reload caddy
```

## Certificate issuance

Caddy's automatic HTTPS is on for both names:

1. On start (or when a name has no usable certificate) Caddy creates/reuses the
   ACME account in `/var/lib/caddy/.local/share/caddy/acme/…` and requests a
   certificate from Let's Encrypt **production** CA.
2. The domain is validated with **HTTP-01**: Let's Encrypt fetches
   `http://fretfight.online/.well-known/acme-challenge/<token>` on **port 80**.
   Caddy serves the token itself, before the redirect to HTTPS, so the redirect
   does not interfere.
3. The certificate is cached in `/var/lib/caddy/.local/share/caddy/certificates/…`
   and loaded from there on every later start. Caddy does **not** re-issue on
   reload/restart while the cached certificate is still valid.

Requirements:

- **Port 80/tcp must stay open** to the internet, otherwise HTTP-01 cannot be
  validated (443 alone is not enough for this challenge type).
- Port 443/tcp must stay open for HTTPS/HTTP-2. Port 443/**udp** must be open
  for HTTP/3; if it is closed, clients silently fall back to HTTP/2 — the site
  keeps working, only the `Alt-Svc: h3` upgrade fails.
- The security group of the VM must not be tightened to the admin IP only.

Rate limits (Let's Encrypt): 5 duplicate certificates per identical set of names
per week, 50 certificates per registered domain per week. That is why the
storage directory below must never be lost or moved.

## Renewal

Nothing to schedule: Caddy renews in-process, in the background, when less than
a third of the certificate lifetime remains — with the 90-day Let's Encrypt
certificates that is **about 30 days before expiry**. The renewal check runs at
startup and then periodically (Caddy's internal maintenance loop), independent
of `systemctl` timers or `cron`.

Renewal writes the new certificate to the same storage directory. A successful
renewal shows up as:

```bash
sudo journalctl -u caddy --since '-30 days' | grep -iE 'renew|obtain|certificate obtained'
```

## Never delete the certificate storage

The certificates and the ACME account live in
`/var/lib/caddy/.local/share/caddy` on the VM disk. Deleting or relocating that
directory (or changing the `storage` option to an ephemeral path) forces a full
re-issuance of both names on the next start and can hit the Let's Encrypt
duplicate limit.

- `docker compose down -v`, `docker compose up --build`, image rebuilds and API
  restarts **cannot** affect the certificates: Caddy is not part of the Compose
  stack and keeps no TLS state in Docker volumes.
- When replacing the VM, copy `/var/lib/caddy` (or at least
  `.local/share/caddy/certificates` and `.local/share/caddy/acme`) before the
  first start of Caddy on the new machine.
- Back it up together with the database:

  ```bash
  sudo tar -czf /var/backups/caddy-$(date +%F).tar.gz -C /var/lib/caddy .local/share/caddy
  ```

## TLS policy

Configured in `deploy/Caddyfile`:

```caddyfile
tls {
	protocols tls1.2 tls1.3
}
```

- TLS 1.2 and TLS 1.3 only; TLS 1.0/1.1 are refused at the handshake.
- TLS 1.3 is preferred by every modern client. Cipher suites are Caddy's
  defaults (AEAD-only for 1.2, all mandatory suites for 1.3); no custom cipher
  list is maintained on purpose.
- ALPN: `h2`, `http/1.1` over TCP; `h3` over QUIC/UDP 443.
- HTTP→HTTPS is a permanent redirect generated by automatic HTTPS
  (`308 Permanent Redirect`, preserves the method and body).
- `www.fretfight.online` has its own certificate and answers
  `301 Moved Permanently` to `https://fretfight.online<path>`.

## Security headers

| Header | Value | Source |
|---|---|---|
| `Strict-Transport-Security` | `max-age=86400` | `app/main.py`, only when the request arrived over HTTPS |
| `X-Content-Type-Options` | `nosniff` | `app/main.py`, every response |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | `app/main.py`, every response |
| `Content-Security-Policy` | strict policy | `app/main.py`, only `/admin*`, `/support`, `/donate` |
| `Alt-Svc` | `h3=":443"` | Caddy (automatic) |

Header policy notes:

- **The application sends the three baseline headers**, not Caddy. Setting them
  in both places produced a duplicated `X-Content-Type-Options` header on
  proxied responses (Caddy appends to the header map the upstream already
  filled). The application is the single source, which also keeps a bare
  `uvicorn` deployment consistent. Caddy sets them only on the `www` redirect
  host, where no upstream exists. Tests: `tests/test_security_headers.py`.
- **HSTS is one day and deliberately not hardened yet.** No `includeSubDomains`
  (subdomains are not all covered by a certificate) and no `preload` (preload is
  effectively irreversible and requires `includeSubDomains`). Raise `max-age`
  and add `includeSubDomains` only after every subdomain is HTTPS-only.
- **No `X-Frame-Options`.** The admin console embeds same-origin `srcdoc`
  previews (`#supportCodePreview`, `#supportPreviewFrame`, both `sandbox=""`), and
  `DENY`/`SAMEORIGIN` at the edge is not worth the risk of breaking them; the
  sandboxed iframes already isolate the content.
- **No CSP on the marketing/player pages.** `/`, `/en`, `/login`, `/register`,
  `/account`, `/policy` contain inline `<script>` blocks (Yandex.Metrika snippet,
  language bootstrap) and inline `style=` attributes, so a policy without
  `'unsafe-inline'` would break them. Only the internal pages, which load no
  third-party scripts, get the strict CSP.

## Verifying from outside

PowerShell (Windows):

```powershell
# headers, HTTP version, certificate subject/issuer/expiry
curl.exe -sI https://fretfight.online/ | Out-String
curl.exe -s -o NUL -w "%{http_version}`n" https://fretfight.online/
curl.exe -sv https://fretfight.online/ 2>&1 | Select-String -Pattern "subject|issuer|expire|TLS"

# redirect and endpoints
curl.exe -sI http://fretfight.online/          # 308 -> https://fretfight.online/
curl.exe -s https://fretfight.online/health/ready
curl.exe -s -o NUL -w "%{http_code}`n" https://fretfight.online/api/v1/songs?limit=2
curl.exe -s -o NUL -w "%{http_code}`n" https://fretfight.online/admin/
```

Linux / from the VM (OpenSSL client, can force protocol versions):

```bash
curl -sI https://fretfight.online/ | head -20
curl -s -o /dev/null -w '%{http_version}\n' https://fretfight.online/     # 2
curl -sI --tlsv1.3 --tls-max 1.3 https://fretfight.online/ | head -1      # works
curl -sI --tlsv1.1 --tls-max 1.1 https://fretfight.online/                # handshake error
openssl s_client -connect fretfight.online:443 -servername fretfight.online </dev/null \
  | openssl x509 -noout -subject -issuer -dates
```

Certificate dates straight from Caddy's cache (the source of truth for renewal):

```bash
sudo openssl x509 -in /var/lib/caddy/.local/share/caddy/certificates/acme-v02.api.letsencrypt.org-directory/fretfight.online/fretfight.online.crt \
  -noout -subject -issuer -dates
sudo ls -l /var/lib/caddy/.local/share/caddy/certificates/acme-v02.api.letsencrypt.org-directory/*/
```

HTTP/3 needs a QUIC-capable client (`curl --http3` from a build with HTTP/3, or
`aioquic`); a browser's devtools "Protocol" column shows `h3` when UDP 443 is
reachable, `h2` otherwise. `Alt-Svc: h3=":443"` being present only means Caddy
advertises HTTP/3, not that the network path works.

**Current state (checked 2026-11-05):** HTTP/3 is served by Caddy — a QUIC
handshake and `h3` GET `/health/ready` against `127.0.0.1:443` on the VM return
`200`, and Caddy listens on UDP/443. From the internet the same QUIC handshake
times out (control: `cloudflare-quic.com` over HTTP/3 works from the same
client), so the VM's security group has no inbound UDP/443 rule. Until that rule
is added in the Yandex Cloud console, browsers use HTTP/2; nothing else breaks.
Add `udp:443` from `0.0.0.0/0` next to `tcp:80`/`tcp:443` and re-test with the
`aioquic` probe / browser devtools.

## Troubleshooting

| Symptom | Check |
|---|---|
| Browser warning / `curl: (60)` | `sudo journalctl -u caddy --since '-15min'`; certificate dates above |
| No certificate obtained, log shows `http-01` timeouts | port 80/tcp in the security group, DNS A record, nothing else on port 80 |
| `too many certificates already issued` | storage directory was wiped or `storage` was changed; wait for the weekly window, then restore the backup from `/var/backups/caddy-*.tar.gz` |
| Site loads but `Alt-Svc` never upgrades to h3 | UDP 443 blocked; HTTP/2 still works, no other impact |
| 502 from Caddy with `Server: Caddy` only | the `api` container is down: `docker compose ps`, `docker compose logs --tail=100 api` |
