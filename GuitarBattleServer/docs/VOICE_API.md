# Lobby Voice Chat API (`/api/v1/voice`)

Голосовой чат в общем лобби Guitar Duels. Клиент JUCE 9.0.2 не умеет открывать
WebSocket/TLS-сокет, поэтому голос передаётся **REST-поллингом**: каждый игрок
отправляет куски PCM (~100 мс) POST-ом и опрашивает куски соперника GET-ом.
Для **прямого UDP** (клиент-клиент, без реле) есть отдельный обмен
эндпоинтами — раздел 5.

- Базовый URL: `https://fretfight.online/api/v1` (в разработке
  `http://localhost:8000/api/v1`).
- Авторизация: `Authorization: Bearer <access_token>` на всех маршрутах.
- Формат: JSON UTF-8. Аудио внутри JSON — base64.
- Кодек: **16 кГц, моно, signed 16-bit little-endian PCM**. Заголовков,
  контейнеров и сжатия нет; клиент сам ресемплит микрофон.
- **Ничего не сохраняется.** Куски живут в памяти процесса 3 секунды,
  UDP-эндпоинты — 30 секунд, файлов нет, payload не логируется. Реле —
  `app/services/voice_relay.py`.

## 1. Кто может звонить

Маршруты доступны только участникам лобби: хосту (`duel_lobbies.host_user_id`)
или гостю (`duel_lobbies.guest_user_id`). Правила берутся из
`app/services/duel_lobby_service.py` (`lobby_member`), отдельных правил у
голоса нет.

| Ситуация | Ответ |
|---|---|
| нет/битый токен | `401` `{"detail": "Invalid or missing access token"}` |
| неизвестное лобби | `404` `{"detail": {"code": "lobby_not_found", "message": "Duel lobby not found"}}` |
| лобби закрыто (`status = "closed"`) | `404`, тот же конверт |
| игрок не хост и не гость | `403` `{"detail": {"code": "not_participant", "message": "You are not a member of this lobby"}}` |
| лобби в статусе `playing` | разрешено (голос не привязан к ожиданию) |

## 2. `POST /api/v1/voice/lobbies/{lobby_id}/chunks`

Тело:

```json
{"data": "<base64 PCM>"}
```

- `data` — непустая строка base64; после декодирования **не больше 6400 байт**
  (200 мс при 16 кГц/16 бит). Больше, битый base64, пустая строка, отсутствие
  поля — `422`.
- Сервер выдаёт `seq`, **монотонно возрастающий для лобби** (глобальный
  счётчик процесса; для каждого лобби он тоже строго растёт).
- Куски хранятся 3 секунды, не более 60 на лобби и не более 20 новейших на
  игрока (старые вытесняются).
- Не более ~10 кусков в секунду на игрока (скользящее окно 1 с). При
  превышении — `429` с телом **строкой**:

```json
{"detail": "voice rate limit"}
```

Ответ `200`:

```json
{"seq": 123}
```

## 3. `GET /api/v1/voice/lobbies/{lobby_id}/chunks?since=0`

Query:

- `since` — `int >= 0`, по умолчанию `0`. Клиент присылает `next_since` из
  предыдущего ответа.

Ответ `200` — только куски **других** участников лобби с `seq > since`,
от старых к новым, максимум 20:

```json
{
  "chunks": [
    {"seq": 124, "user_id": "6e2f...", "username": "styr", "data": "<base64>"}
  ],
  "next_since": 124
}
```

- `next_since` — максимальный `seq`, который сейчас **хранится** для лобби
  (включая собственные куски вызывающего), либо `since`, если буфер пуст.
  Назад не уменьшается: `next_since = max(since, newest_stored_seq)`.
- Собственные куски не возвращаются никогда.
- Пустой буфер — `{"chunks": [], "next_since": <since>}`.

## 4. `DELETE /api/v1/voice/lobbies/{lobby_id}/chunks`

Очищает буфер вызывающего игрока. Ответ `204`, тела нет. Идемпотентно.
Вызывать при выключении микрофона и при выходе из лобби.

Закрытие лобби хостом (`POST /duels/lobbies/{id}/leave`) освобождает буфер
всего лобби; выход гостя — только его собственные куски.

## 5. `POST /api/v1/voice/lobbies/{lobby_id}/endpoint`

Обмен UDP-эндпоинтами для **прямого голоса** (клиент-клиент, без реле). Клиент
открывает UDP-сокет на эфемерном локальном порту, присылает только порт, а
публичный IP сервер определяет сам по соединению.

Тело:

```json
{"port": 49152}
```

- `port` — **целое** `1..65535` (`strict`: строка `"49152"` и `49152.0` — `422`).
- Поля `ip`, `public_ip` и любые другие игнорируются: адрес клиента никогда
  не принимается из тела. IP берётся из `X-Forwarded-For` (первый адрес
  цепочки, Caddy дописывает непосредственного пира) или, при прямом
  соединении без прокси, из адреса сокета (`app/services/client_ip.py`).
- Если адрес определить нельзя (заголовка нет и сокет — не IP, либо в
  заголовке приватный/loopback-адрес), ответ `400`:

```json
{"detail": {"code": "client_ip_unavailable", "message": "The public IP of this connection cannot be determined"}}
```

Ответ `200`:

```json
{
  "ip": "203.0.113.5",
  "port": 49152,
  "peer": {"ip": "198.51.100.7", "port": 50001}
}
```

- `ip`/`port` — **собственный** эндпоинт вызывающего (IP, как его видит сервер;
  порт эхом из запроса).
- `peer` — эндпоинт **другого** участника лобби (`null`, если он ещё не
  публиковал порт, вышел или его запись истекла). Свой эндпоинт в `peer`
  не попадает никогда.
- Хост в комнате без гостя всегда получает `peer: null`.
- Запись обновляется на каждом POST (клиент шлёт его периодически, например
  раз в 10 секунд) и живёт **30 секунд** (`ENDPOINT_TTL_SECONDS`). Просроченные
  записи удаляются при чтении и при записи. Ничего не сохраняется на диск.
- Ошибки доступа те же, что у `/chunks`: `401` без токена, `404` для
  неизвестного/закрытого лобби, `403` для не-участника. `playing` разрешён.
- Выход гостя и закрытие комнаты хостом удаляют эндпоинт вместе с голосовыми
  кусками (`duel_lobby_service.leave_room` → `voice_relay.clear_user` /
  `clear_lobby`).

## 6. Ограничения и риски

- Реле **только для одного процесса**: production запускает один uvicorn
  worker (`docker/entrypoint.sh`, без `--workers`). При нескольких воркерах
  понадобится общий бэкенд (Redis).
- Память на лобби ограничена: `60 * 6400` байт ≈ 384 КиБ плюс заголовки.
  Записи лобби исчезают из реестра, когда в них не остаётся ни кусков, ни
  отметок rate limit, ни UDP-эндпоинтов.
- UDP-эндпоинты лежат в том же реестре: максимум две записи на лобби (по одной
  на участника) с TTL 30 с. Рестарт процесса их теряет — клиент обязан
  публиковать порт при каждом входе в комнату, а не один раз за сессию.
- Голос — best effort: при потере куска (поллинг реже 1 раза в 3 с) он
  пропадает, повторов и подтверждений нет.
- Пропускная способность: 10 кусков по 6400 байт в секунду — это ≈ 62 КБ/с
  PCM (≈ 85 КБ/с с учётом base64) на игрока в каждую сторону.
